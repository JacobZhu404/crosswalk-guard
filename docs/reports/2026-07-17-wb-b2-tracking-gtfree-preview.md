# B2 跟踪评测 · GT-free 预览（下界）

> 状态：首轮 GT-free 趋势报告，交 cc 审阅。尚未占用 Jacob 标框（GT-anchored 精版待 cc 决定）。
> **⚠️ 下界 / 代理指标，非模块真值**：窗口与代表车来自系统自身检测（`decide()` 返回的 episode 的 `start_ts/end_ts` + `member_tracks`），不是 GT 标框。它只能反映"已检出违章窗内跟踪稳不稳"，**不能度量因跟踪失败导致的漏检**。下文所有数字打"下界"标签。

## 方法

- 脚本：`scripts/eval_tracking_gtfree.py`（新建，不碰 `tracker.py`、不改现有 `eval_tracking.py` 脚手架）。
- Pipeline 与锚点 **完全一致**：`CrosswalkDetectorV2` + `occ_denom=box` + `preset=balanced`（即 0.889 锚点的同款配置）。跟踪本身只依赖车辆框，与斑马线检测器无关，故碎片化是 **tracker 固有属性**。
- 取数：`cli.run(return_track_samples=True)` → `(events, track_samples)`；逐 episode 用其 `member_tracks`（碎片合并后的所有 track_id）+ 窗内逐帧 box 最近代表框者算"主导 tid"。
- 视频：9 个有违章的视频（02–09、11）。04 未检出违章事件（即端到端已知的短绿漏检 fn=1），无窗口可锚 → 跳过。故 8 个事件。
- 指标：
  - **碎片数 = `len(member_tracks)`**：物理同车被切成几个 ID（上界/代理）。
  - **ID 切换**：窗内逐帧"主导 tid"变化次数（跨 None 不计数）→ 反映多 ID 是否**同时活着**（交错）。
  - 断裂 / 覆盖率：见下方"方法学 caveat"。

## 核心发现

1. **跟踪碎片化是普遍且严重的盲点**：8/8 违章视频碎片数 ≥5，均值 18、最高 45（一辆车在 106s 内被切成 45 个 ID）。此前端到端 F1=0.889、覆盖=0.904 完全看不出——因为 **engine 的时间合并（`decide()` 的 `member_tracks` + gap 合并）把碎片 ID 缝回了单个 episode**。
2. **断裂=0、覆盖=1.000 不是"跟踪稳"，是"车没丢"**：违章车每帧都被某个 track 覆盖（只是 ID 在变）。这是**纯 ID 重编号抖动**，不是跟踪丢失。
3. **两种碎片化形态**：
   - **交错型**（02/05/08/09，ID切换 19–36）：多个 ID 同时活着 → 主导 tid 频繁跳变 → 最危险（任何依赖稳定 ID 的逻辑都会抖）。
   - **顺序型**（07/11，碎片数>1 但 ID切换=0）：ID 先后衔接、不重叠 → 相对温和，但仍被切成多段。
4. **风险面（当前被合并掩盖）**：
   - 端到端指标对碎片化**免疫**——所以现在不修也不回退。但一旦改动合并逻辑（gap 收紧 / 引入 ID 依赖）或部署到更难视频，抖动会直接变现为误检/漏检。
   - `PlateConsensus(keep_history=180)` 依赖跟踪稳定：频繁重编号会**重置车牌历史**，可能削弱车牌共识鲁棒性（值得单列验证，不在本预览范围）。

## 方法学 caveat（诚实标注，避免误读）

- **覆盖率 / 断裂近乎同义反复**：窗口来自系统自身 occupancy 检测，车必然在窗口内被某 track 覆盖 → 覆盖≈1、断裂≈0 是构造性的，**不携带新信息**。本预览真正有信息量的是 **碎片数 / ID 切换**。
- **碎片数是上界**：`member_tracks` = 合并进 episode 的所有 track_id。若合并阈值（gap）偏松，相邻**不同车**的违章区间也可能被并入 → 碎片数偏高。对单车间违章（GT 每窗一车）而言 17–45 基本是重编号；但精确"哪些 member 是同一辆车"需 GT-anchored 精版用 Jacob 标框的 IoU 归属来确认。
- **04 缺席**是灯态短绿漏检（已知 fn=1），与跟踪无关。
