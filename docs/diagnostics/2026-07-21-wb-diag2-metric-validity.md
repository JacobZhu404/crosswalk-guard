# Diag 2 — 评测指标矛盾（measurements-disagree）：灯态准确率是不是自证循环？

> **性质**：只读诊断（不改代码、不重训、不重挖）。仅读 `identify_pedestrian_signal.py` 与 `eval_temporal_fusion.py` / `eval_light_fast.py` 的逻辑 + 对照 cc 硬 GT（05/06/09 IoU=0）。
> **目的**：解释 git log 里"修 prior 提升灯态准确率"（472d9a1 / 8b863f1 / 8e6f6d2 / c26b3f3）与"真值显示 05/06/09 prior IoU=0"的矛盾——指标到底测什么、为何偏框 prior 也能涨。
> **结论先行**：**是自证循环（self-confirmation loop）**。prior 是为"匹配 GT 时间线"而选的位置，评测又在"该 prior 处采样"去比同一个 GT——结构上必然高一致，与"prior 是否真的框住灯"无关。cc 的硬 GT（IoU=0）直接证伪了历史"准确率提升=修对了"的叙事。**所有以该协议得出的"准确率"数字都应降级为"相对回归指标"，不可再当正确性证据。**

---

## 1. 自证循环的机制（代码实证）

### 1.1 prior 是为匹配 GT 而选的（原因）
`scripts/identify_pedestrian_signal.py`（`identify()`，约 91–157 行）：
- 把每帧检出的候选信号头按 (cx,cy) 聚类；
- **对每个候选头，用其颜色时间线与 GT `label_result_*.csv` 的灯态时间线打分**（匹配率 + 覆盖度）；
- **返回"匹配 GT 时间线最高"的那个头的位置 (cx,cy) 作为 `signal_prior`**。

→ 即：**prior 的位置 = 在该视频里"颜色时间线最像 GT"的位置**。它优化的是"采样此处能复现 GT 时间线"，不是"此处是真灯"。

### 1.2 评测在 prior 处采样去比 GT（果）
`scripts/eval_temporal_fusion.py`（约 32–57 行 `load_priors` + `eval_video`）：
- `det.signal_prior = (cx,cy)`、`det.prior_roi_px = roi` 喂给 `observe()`；
- `observe()` 在 prior ROI 采样 → 检测器判色 → `fuse_light` 出时间线；
- 拿这条时间线 vs `datasets/gt/light_states.csv` 算准确率。

→ 因为 prior 本就是"按 GT 时间线选"的位置，评测在**同一个位置**采样去比**同一份 GT**，高一致是**被构造出来的**，不是检测正确的证据。

### 1.3 闭环节点
```
GT 时间线 ──(identify 选位置)──> prior 位置 ──(eval 在 prior 处采样)──> 预测时间线 ──比 GT──> "高准确率"
      ^__________________________________________________________________________|
```
GT 既决定了 prior 位置，又作为评测基准 → 闭环。无论 prior 是否框住真灯，只要"在那采到的颜色"能复现 GT 时间线，指标就高。

---

## 2. 铁证：偏框 prior（IoU=0）也能"涨准确率"

cc 用标注工具画的硬 GT 显示：**05 / 06 / 09 的 prior IoU=0**（完全没框住真灯，09 偏移达 0.43 到对侧），且框普遍大 3 倍。按常理这些 prior 应导致"完全检不到真灯 → 准确率崩"。但 git log 显示的却相反：

| commit | 声称的准确率变化 | 涉及视频 |
|---|---|---|
| `472d9a1` | 修 prior 位置 57%→72% | 03 |
| `8b863f1` | 修 prior "盲区全不及格→修 prior 改善" | 01/05/06/07 |
| `8e6f6d2` | 修 GT+prior 72.8%→98.2% | 01 |
| `c26b3f3` | 07 prior 上挪 86.5%→91.6%，11 保持 | 07/11 |

- `8b863f1` 专门动了 05/06 的 prior，且报告"修 prior 改善"——但 cc 硬 GT 显示 05/06 的 prior **IoU=0**。
- 矛盾的唯一合理解释：**指标测的是"prior 处采到的颜色是否匹配 GT 时间线"，而非"prior 是否框住真灯"**。所谓"修 prior 提升准确率"，提升的是"采样位置对 GT 时间线的还原性"，与定位正确性无关。偏框 prior 若在错误位置仍能采到与 GT 同相位的红/绿（例如背景里恰有同色反光、或该视频主状态单一），指标照样高。

→ 这坐实了自证循环：**准确率数字无法区分"框住真灯"与"在错处采到同色"**。

---

## 3. 指标还能用吗？——能"相对"不能"绝对"

| 用途 | 是否有效 | 说明 |
|---|---|---|
| 检测**相对回归**（某次改动后数字掉了 = 管线某处坏了） | ✅ 可用 | 闭环未破，变化量仍反映 pipeline 变化 |
| 作为**正确性 / 定位准确率**证据（"修对了""准确率 X%") | ❌ 不可信 | 自证循环 + IoU=0 反例 |
| 判定 prior 是否真的框住灯 | ❌ 不可信 | 指标与定位无关 |

**哪些历史数字要重估**：所有走 `eval_temporal_fusion.py` / `eval_light_fast.py`（prior 采样 vs `light_states.csv`）协议、且 prior 经 `identify_pedestrian_signal.py` GT 调过的"准确率"声明——至少 `472d9a1` / `8b863f1` / `8e6f6d2` / `c26b3f3` 四条，及其衍生的"prior 修对→灯态准确率提升"叙事。这些数字**不代表真实检测正确率**。

---

## 4. 对 Diag 1 数字的连带修正

Diag 1 里的 89.5%（纯 prior）/ 97.3%（含 YOLO）绝对准确率，**同源自该自证循环**，因此：
- 绝对数字 ≠ 真实正确率，只能当"相对指示"。
- **唯一可直接采信的是相对量**：关 YOLO 让 06 从 90.7%→60.3%（塌 30pp）。这一 Δ 不依赖指标是否自证——它隔离的是"YOLO 的边际贡献"，而 YOLO 路径不依赖 prior 选址，故该 Δ 是干净的。

---

## 5. 建议：换一个"位置可验证"的指标再下结论

在 `light_priors.json` 重定位（Jacob 画框完成后）之前，任何"准确率"都不可作为放行/判决依据。可考虑的**非自证**验证：
1. **位置验证优先**：用 cc 硬 GT 框算 prior 的 IoU / 中心点距离，先保证 prior 框住真灯（IoU>0、偏移<阈值），再谈下游。
2. **端到端独立校验**：重定位后，用**未被 prior 选址过程污染**的 GT（Jacob 硬框）做 observe() 输出 vs 硬框灯态的比对，而非 vs `label_result_*.csv` 时间线。
3. **保留旧指标作回归哨兵**：仍跑 `eval_temporal_fusion.py`，但只用于"数字突变报警"，不用于"证明正确"。

---

## 6. 结论

- **矛盾已解**：git log "修 prior 涨准确率" 与 "05/06/09 IoU=0" 不冲突——因为指标是自证循环，测的是"prior 处采色复现 GT 时间线"，与定位正确性脱钩。
- **历史数字需重估**：`472d9a1` / `8b863f1` / `8e6f6d2` / `c26b3f3` 的"准确率提升"声明不可再当正确性证据；prior 是否真的框住灯，须用位置级验证（IoU）另测。
- **对当前工作的含义**：Phase B 的四关 gate、Step0/Step2 的所有"准确率"读数都来自此指标，**在 prior 重定位 + 指标换血前，任何基于旧准确率的"达标/未达标"结论都需打折扣**。这正是 cc 叫停 Step2 sweep、转向"先重定位 prior → 干净重挖 → 再重训"的根因逻辑闭环。
